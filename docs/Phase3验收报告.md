## 二、原文锚点设计（本轮核心）

### 2.1 锚点里存什么

```jsonc
{
  "paperId": "全局论文 id", // 批注属于论文，不属于项目
  "pdfSha256": "PDF 文件内容哈希", // 创建这条高亮时用的是哪一份文件
  "page": 3, // 1 起的页码
  "quote": "规范化后的原文", // 空白折叠 + 首尾去空
  "prefix": "前面 40 字", // 用于消歧
  "suffix": "后面 40 字",
  "rects": [{ "x": 0.13, "y": 0.42, "width": 0.38, "height": 0.017 }], // 页面比例，不是像素
}
```

**不存什么**：不存 DOM 节点、元素 id、`TextItem` 下标、像素坐标、滚动位置、React 状态。锚点的每一部分都能在重新渲染后重新求值。

### 2.2 为什么是这样的组合

| 字段            | 作用                                 | 为什么不能少                                     |
| --------------- | ------------------------------------ | ------------------------------------------------ |
| `pdfSha256`     | 说明锚点描述的是**哪一份文件**的文本 | 换文件后文本可能完全不同，套用旧锚点等于随机高亮 |
| `page`          | 定位到页                             | 页面文本索引只在页内有意义                       |
| `quote`         | 要找回的那段原文                     | 没有它就无法确认"还是这段字"                     |
| `prefix/suffix` | 区分同一页上重复出现的文字           | 只有引文时无法区分两次出现，只能猜               |
| `rects`         | 页面比例坐标，用于**绘制**           | 与缩放/窗口宽度无关；同一份文件下它就是权威几何  |

绘制用 `rects`，定位校验用 `quote + prefix/suffix`。两者分工明确：`rects` 保证"画在原来的位置"，文本匹配保证"那段字还在那儿"，并在不成立时**明确报告**。

### 2.3 匹配策略（保守优先）

```
在同一页的渲染文本里找出 quote 的所有出现位置
  → 0 处            : missing（报告"没有找到"，不猜）
  → 1 处            : found
  → 多处            : 按 prefix/suffix 与页面的重合字符数打分
      最高分严格领先 → found（用胜出那处）
      最高分并列     → ambiguous（报告"出现了多次，无法确定"，不高亮到任何一处）
```

- 页面文本按**渲染出来的文本层**构建（span 顺序 + `<br>` 换行），与用户拖选时浏览器给出的文本同一口径，因此选区与索引天然一致。
- 上下文**折叠空白但不去首尾空格**：`prefix` 末尾的空格是它与页面文本对齐的一部分，去掉就会让所有候选位置上打分归零（这个 bug 本轮真的踩到了，见第六节）。
- 行末断行、跨多个 span 的选择、嵌套 span（pdf.js 的 `markedContent`）都在测试覆盖内。

### 2.4 锚定正确性 > 匹配成功率

这是本轮最重要的取舍：**宁可说"我无法唯一定位"，也不把高亮画到另一段相似文字上**。`verify:annotations` 里有一条专门构造的用例——把一条锚点的上下文清空后重新打开，点击"回到原文"必须出现"这段原文在这一页出现了多次"的提示，而不是默默跳到第一处。另一条反向用例：上下文完整时，同一页两次出现的句子能被正确区分，不报歧义。

### 2.5 文件被替换时

`pdfSha256` 与当前打开的文件不一致时：**批注保留**，但**不画在新文件上**，并在笔记面板里单独分成「另一份 PDF 上的笔记」，附一句解释，且"回到原文"按钮禁用（实测：替换文件后 `0 highlights drawn`，笔记仍在）。这满足"不得默认将旧锚点应用于新 PDF"，也没有删用户的数据。

## 三、数据结构与 Schema 变化

Schema 从 **v3 → v4**，走既有迁移机制（`MIGRATIONS` 表新增 `3 → 4`）：

```ts
interface Annotation {
  // 顶层新增 annotations: Annotation[]
  id: string; // 独立稳定 id（crypto.randomUUID）
  paperId: string; // 全局 Paper.id
  pdfSha256: string;
  page: number;
  quote: string;
  prefix: string;
  suffix: string;
  rects: NormalizedRect[]; // 比例坐标，已与页面求交
  kind: 'question' | 'insight' | 'note';
  note: string;
  createdAt: number;
  updatedAt: number;
}
```

| 决定                                 | 理由                                                                                            |
| ------------------------------------ | ----------------------------------------------------------------------------------------------- |
| 批注放在 LocalStorage 主文档里（v4） | 与论文注册表同一次写入、同一份事实来源，复用既有迁移/隔离/备份保护；批注是文本，量级只有几十 KB |
| 按 `paperId` 归属，而不是按项目      | 「同一篇论文在不同项目里看到相同批注」直接由数据模型保证；实测跨项目复用通过                    |
| 删除项目不动批注                     | reducer 的 `remove` 只删项目；单测断言批注与论文注册表原样保留                                  |
| 修改论文标题/标识符不动锚点          | 锚点只认 `paperId` + 文本 + 比例坐标，与元数据无关（单测覆盖）                                  |
| 锚点与笔记分开存                     | `quote/rects/...` 与 `note/kind` 是两类信息：前者不可编辑，后者可编辑                           |
| 旧载荷缺 `annotations` 视为空列表    | v3 载荷本来就没有这个字段；形状不对才是损坏                                                     |

迁移两处都实测过：v3 载荷升到 v4 后数据不变、只多一个空列表；v2/v1 载荷继续走完整链条（`npm run check` 里的迁移用例覆盖 1→4 链）。

## 十、未解决的技术限制

1. **没有用真实论文验证过**：全部样本是生成的。真实论文的图表、多栏浮动体、脚注、公式排版未覆盖，应作为"生成样本验证"看待。
2. **跨页选择被拒绝**（有提示）。跨页锚点需要把多条锚点串成一个逻辑批注，本轮没做。
3. **连字符断词不还原**：`hyphen-\nation` 在重新匹配时不会被拼回 `hyphenation`，可能判为 missing（会如实报告，不会错标）。
4. **扫描页无法高亮**（无文本层，已提示）；OCR 明确不在本轮范围。
5. **锚点几何来自创建时的浏览器测量**：同一文件下它就是权威值；若将来 pdf.js 改变文本层布局，`rects` 可能与新渲染略有出入——文本匹配是发现这种情况的检查（会报 missing/ambiguous），但没有自动重算机制。
6. **批注没有导出/导入**，也没有跨论文搜索；面板只按页码排序，没有筛选与全文检索。
7. **批注存在主文档里**：数万条量级会开始压迫 LocalStorage（约 5MB）上限，届时应迁到 IndexedDB（`PdfBlobStore` 的抽象已经在了，但批注是版本化文档的一部分，迁移需要一次 Schema 升级）。
8. **`Paper.reading` 与批注都在论文级**，不是"每个项目各自的阅读进度"；如果将来需要按项目区分阅读状态，需要再拆一层。
9. **Tauri 未接入**（本轮禁止项）：桌面壳下 PDF 字节应落文件系统，届时 `pdfSha256` 的语义要在新存储下复核。

## 十一、Agent 执行效率复盘

口径同前：拿不到 token 用量与账单，下面只描述可观察的工作构成，不含任何 token/费用估算。本轮未调用其他 AI 模型或子代理。

**有效开发**：新增 12 个源文件（领域 1、阅读器 4、脚本 3、测试 4），扩展样本库与样式；核心决策只有三个：锚点存什么（文本 + 上下文 + 比例坐标，不存 DOM）、匹配怎么定（多重匹配必须靠上下文，否则报歧义）、批注归谁（`paperId`，不是项目）。

**测试与验收**：单测全量 3 次；`npm run check` 3 次；`npm run build` 6 次；四套浏览器验收各跑 1–2 次；`verify:annotations` 单独跑了 **7 轮**才全绿，每一轮都有新的诊断输出（滚动轨迹、按钮名列表、状态转储、几何偏差数值），没有"同样失败重跑"。

**重复与低效操作（如实列出）**：

1. **同一个文件连续 4 次用 Python 替换正文失败**（因为 Prettier 在我写完之后重排了格式，替换字符串不再匹配），每次都浪费一次往返才发现。教训明确：改这个脚本应该一开始就用 Edit 工具，而不是 bash+python。
2. 浏览器验收里我先后写错了 3 个定位（`笔记` 子串撞上 4 个按钮、`filter({hasText})` 同时命中 3 行、选择范围差 1 个字符）。前两个是 Playwright 严格模式本来就会报错的"好错误"，第三个是我自己数错字符——为此多跑了一轮。
3. 一条检查（`reload: 位置不变`）第一版比较的是视口坐标，必然包含滚动量，等于写了个假检查；发现后改成按页面比例比较，顺带把结论从"看起来没动"变成"0.0‰"。
4. jsdom 里 pdf.js 的 fake worker 起不来（模块解析问题），我花了一次探测确认这是测试环境限制而不是应用缺陷，随后改为"组件级单测 + 浏览器端到端"的组合。

**没有做的事**：没有通读全工程；没有为凑数写断言；没有为了让验收变绿而放宽锚定精度（相反，第六节第 1、2 条正是"宁可报错也不猜"的实现）；没有引入批注框架或富文本编辑器，编辑器就是一个 textarea。
