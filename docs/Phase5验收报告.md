# Phase 5 验收报告：沉浸式阅读体验与主动难点辅助

日期：2026-10-17。工作目录：`D:\论文阅读解构项目`。分支：`phase5-immersive-reading`（从 Phase 4.2 已验收提交 `b0779ad` 建）。

## 一、结论

1. **PDF 页面本身可以换纸了。** 原始 / 暖纸 / 深灰三种模式，改的是画布像素，不是外层容器。浅色主题下默认暖纸 `(246,241,230)`，深色主题下默认深灰 `(35,38,43)`，墨色转为 `(214,217,222)`；试纸上的红色与蓝色块在三种模式下**逐像素不变**。选择会记住，刷新后仍在，也能切回「跟随外观」。
2. **不做整幅反色。** 像素按**色度**分流：接近中性灰的是墨与纸，走调色表；有彩色度的是图，原样保留。整页暗像素超过 35% 的页面判定为图像页，**拒绝重着色**并在角落说明——那正是「不能可靠重着色」时的回退。
3. **AI 助手成了常驻入口。** 顶部「AI 答疑」按钮移除，右侧面板带 AI / 难点 / 笔记三个页签，收起后留一条窄轨道。**不选中文字也能提问**：只发当前页正文（实测 153 字），面板明说范围；会话在关面板、翻页后都还在。
4. **「向这段文字提问」**成为浮动工具条上的按钮，沿用既有锚点与上下文披露；实测发送的正是选中的 103 字。
5. **智能难点**：服务端只保证「引文逐字来自这一页」，定位交给浏览器复用 Phase 3 的保守匹配（唯一才标）。一次只分析当前页，缓存键含文件哈希与规则版本，换文件不继承；建议可忽略、可整体隐藏、可存为笔记、可继续追问；被丢弃的引文不会变成标记（mock 故意混入一条，实测被服务端丢掉）。
6. **一次真实调用事故**：我的验收脚本漏传 `AI_PORT`，页面请求绕过了离线服务、打到了仍在运行的付费 DeepSeek 服务，产生 **2 次真实调用**。详见第二节。已修复并加了机制性护栏。

## 二、本轮事故：2 次真实调用

任务书写明「本轮施工和自动化验收仅允许 Mock Provider」。**我违反了这一条，不是有意，但确实发生了。**

### 发生了什么

`scripts/verify/immersive.mjs` 启动 `vite preview` 时把环境变量原样传下去，**漏了 `AI_PORT`**。`vite.config.ts` 的代理目标是 `process.env.AI_PORT ?? '8787'`，于是页面里的 `/api/ai/*` 全部走到了 **8787**——Phase 4.1 联调时由用户启动、至今仍在运行的真实 DeepSeek 服务。

暴露它的是 `POST /api/ai/difficulties` 返回 **404**：那个进程跑的是 Phase 5 之前的代码，没有这条路由。既然 404 来自它，说明代理确实指向它——同一代理上的两次 `/api/ai/ask` 也就落在了同一个服务上。

### 影响

- **2 次真实模型调用**（页面提问 1 次、选区提问 1 次），论文内容是合成的测试纸（不含真实论文）。
- 按 Phase 4.1 同量级估算，合计 **< $0.01**；**没有账单核对**，这个数字是估算。
- 离线服务（我自己启动的 mock）那次运行里**一次都没有被用到**。

### 为什么没被既有护栏拦住

Phase 4.2 的护栏都在，但它们检查的是「**我启动的那个服务**」的身份，而这次请求根本没到它那里。缺口在于：**预览服务器把请求转给了谁**，从来没有人核对过。

### 修复

1. `startPreview` 现在显式传 `AI_PORT`。
2. 新增一条**经过代理的身份校验**：预览起来后、打开浏览器之前，先 `fetch(预览地址 + /api/ai/health)`，必须读到 `provider: "mock"` 且 `online: false`，否则立刻杀掉子进程并 `exit 4`。校验的是页面真正会走的路径，不是我以为它会走的路径。
3. 同一条校验**也加进了 `verify:ai`**——它虽然一直传了 `AI_PORT`，但一直没验证过代理的终点。

### 教训

「服务是 mock」和「页面在跟 mock 说话」是两件事。前者上一轮做过，后者这一轮才做。剩下的风险是那个付费服务一直开在 8787：**建议用户验收后把它停掉**。

## 三、Task A：纸张深浅色与护眼模式

### 3.1 方案：按色度分流，不按亮度反色

约束写得很清楚：不许整幅反色，也不许假定亮度能可靠区分文字与图片。做法是：

| 像素            | 判据                            | 处理                                             |
| --------------- | ------------------------------- | ------------------------------------------------ |
| 近中性（墨与纸） | `max−min ≤ 24`                  | 走 256 级调色表，映射到目标纸色与墨色            |
| 有彩色（图）     | `max−min > 24`                  | **原样保留**，三种模式都不动                     |
| 透明像素        | `alpha = 0`                     | 不涂（渲染时已让 pdf.js 铺白底，正常不会出现）   |
| 整页过暗         | 暗像素占比 > 35%，且页 ≥ 4096 像素 | **拒绝重着色**，按原始颜色显示，角落标注原因     |

- 色度阈值 24 是在本项目两篇真实论文上定的：正文黑字的色度不超过 12，任何彩色图元都远高于 24。
- 调色表端点做了吸附：`L ≥ 250` 直接落到纸色，`L ≤ 5` 直接落到墨色，避免页面底色与样式表颜色差几个单位、在纸边露出接缝。
- 渲染时给 `page.render()` 传 `background: '#ffffff'`：先铺白，再按 PDF 内容绘制，最后整体改色。这一步让「不画的地方」也变成纸色，而不是把透明当成墨。
- 重着色在**独立的工作画布**上做（`willReadFrequently`），再贴回可见画布：直接对可见画布 `getImageData` 会让 Chromium 每页报一次警告。

**已知会出错的一类**：灰度照片/灰度填充——它们本身就是中性色，规则无法区分「照片里的深灰」与「墨」。灰色块在深灰模式下会被当成墨变亮（截图 `01-paper-dark.png` 里那块灰方块可见）。这是本方案的边界，不假装解决：整页图像密集时会被 35% 规则拦下，单张灰度图则没有拦。**读者可以一键切回「原始」。**

### 3.2 模式与持久化

- 四个选择：跟随外观 / 原始 / 暖纸 / 深灰，存在 `rw.paper`。
- 「跟随外观」下：应用浅色 → 暖纸，应用深色 → 深灰；系统主题变化会跟着变（`useTheme` 的 `matchMedia` 已经覆盖）。
- 手动选择后不再跟随，刷新、换论文都保留（实测：切深灰 → 刷新 → 仍是深灰）。

### 3.3 与既有的高亮、选区、文字层的关系

- 高亮是 `multiply` 混合，在白纸上成立；深色纸上改为 `screen`，否则会被乘成黑块。
- 选区色在深色纸上提高到 58%，否则看不出选中。
- 文字层仍是透明文字，坐标来自 pdf.js，与纸张颜色无关；实测换模式前后高亮框与重新选区的偏差 **0.0px**。

### 3.4 实测数字（浏览器，真实画布像素）

| 检查                       | 结果                                              |
| -------------------------- | ------------------------------------------------- |
| 浅色主题默认暖纸           | 纸 `(246,241,230)`                                |
| 暖纸下彩色保真             | 红 `(217,26,26)`、蓝 `(26,115,217)`，与原始一致   |
| 原始模式                   | 纸 `(255,255,255)`，平均亮度 229                  |
| 深灰模式                   | 纸 `(35,38,43)`，全页平均亮度 49，最亮 253        |
| 深灰下彩色保真             | 红、蓝与原始模式逐像素一致                        |
| 换模式后高亮对齐           | 模式间 0.0px，与重新选择 0.0px                    |
| 刷新后模式                 | 仍是深灰（亮度 38）                               |
| 跟随外观 + 切浅色          | 纸回到亮度 241                                    |

## 四、Task B：常驻式 AI 阅读助手

### 4.1 入口

- 顶部「AI 答疑」按钮**已移除**；阅读器顶栏保留页码、缩放、适应宽度与纸张模式。
- 右侧统一面板：AI 助手 / 难点 / 我的笔记 三个页签，面板收起后右侧留一条窄轨道（AI、难点、笔记三个图标，带计数）。
- 面板开合会改变阅读列宽度，`fit-width` 随之重算。**新增了阅读位置保持**：以「页 + 页内比例」为锚点，宽度变化后回到原处（这是本轮修掉的一个真实缺陷，见 8.1）。

### 4.2 没有选区也能提问

- 打开助手即是「关于这一页」的对话入口，提供三个开场问题（这一页讲了什么 / 核心方法是什么 / 哪里容易卡住）。
- 请求新增 `scope: 'selection' | 'page'`：
  - `page`：只发**当前这一页**的正文（受既有 2000 字上限约束），一块段落，id 为 `page`；
  - `selection`：与原来完全一致（选中段 + 同页上下文）。
- 服务端据此改写提示词中的范围说明，并明确要求「缺少依据就直说，不要假设整篇论文」。**系统消息逐字节不变**（有测试守着）——范围描述的是材料，材料永远不进系统消息。
- 面板顶部照旧显示「第 N 页整页 / 选中 X 字 —— 查看会发送的范围」。
- 实测：页面提问发出的请求是 `scope=page`、仅 1 段、153 字。

### 4.3 选区提问

- 浮动工具条上的按钮改名为**「向这段文字提问」**，与高亮、笔记并列；点开仍是原来的五个意图 + 自由提问。
- 实测：发送的正是选中的 103 字（`scope=selection`）。
- 只是选中文字**不会**触发任何调用；调用只发生在点击之后。

### 4.4 会话保持

- 会话存在 `ReaderView` 的状态里：关面板、翻页、切页签都不清空（实测：关闭再打开，轮次数不变）。
- 切换论文会重开阅读器（`key={paper.id}`），会话随之重置——这是刻意的。
- 整页对话的回答没有可锚定的原文，因此「保存为笔记」被禁用并给出原因，而不是伪造一个覆盖整页的高亮。

## 五、Task C：论文核心难点的自动识别

### 5.1 识别什么、不识别什么

服务端的系统消息（常量）里写明：只标核心技术概念、首次出现的重要定义、定理与前提、关键公式与符号、算法步骤、设计选择、必要的前置知识；**一页最多 5 条，宁少勿多**；凑数的条目比没有更糟。类型限定在七个枚举里（`concept/definition/theorem/formula/algorithm/design/prerequisite`）。

### 5.2 工作机制与费用边界

- **一次一页**。请求只带当前页正文（≤4000 字），不带论文其它页。
- **默认关闭**。首次启用是一张说明卡：发送范围（只这一页）、费用（在线时明说「每一次分析都可能产生费用」）、覆盖范围（不会扫描整篇论文）、缓存（翻回来不重复发送）、影响（不写入笔记）。在线服务下按钮文字直接写成「开始分析（会调用在线模型）」。
- 启用后，读者停在一页约 1.2 秒才分析；失败过的页不会自动重试，只在面板里提供「重试这一页」。
- 分析失败只写进面板的错误行，**不影响阅读、批注、位置**。
- 应用启动、刷新、导入 PDF 都不会触发分析（有检查断言启用前请求数为 0）。

### 5.3 数据结构与缓存

- 独立 domain：`DifficultySuggestion`（论文 / 文件哈希 / 页 / 类型 / 名称 / 为什么 / 通俗解释 / 进阶提示 / 引用 / 定位状态 / 锚点 / 模型 / 时间）。
- **独立存储**：`rw.difficulties` 与 `rw.difficulties.prefs`，**完全不碰 `rw.projects`**。缓存坏了就当空，不做隔离副本——它是可再生的派生数据。
- 缓存键 = `pdfSha256 | page | model | rulesVersion`。换 PDF 自然失效；规则版本由服务端回传（`d1`），改规则即等于换键，旧结果只是「不被用」，不会被删。
- 有上限（400 页，按分析时间淘汰）与「忽略列表」（按文件哈希）。
- 实测：刷新后**没有发出任何分析请求**，标记从缓存里回来。

### 5.4 定位与视觉

- 服务端只做一件事：`quote` 必须是本次发送页面正文的逐字子串，否则丢弃并计数。**不定位**。
- 浏览器用 `locateAnchor`（Phase 3 的保守匹配）：唯一命中才画标记；歧义或找不到时仍保留这条建议，标为「位置有歧义，未标注 / 原文中找不到，未标注」，**绝不猜位置**。
- 标记是文字下沿的一条**虚线下划线**（可点，10px 命中区），不是填充色块，不遮挡文字，也不会被误认为读者的高亮（数据层、图层、样式都分开）。
- 点击标记弹出卡片：类型、名称、**1–3 句通俗解释**、为什么值得理解、三个动作（深入理解 / 存为笔记 / 忽略）、以及一句「AI 建议，不是原文；它的引文只保证逐字出现在这一页里」。
- 面板可整体隐藏标记（建议仍在列表里）、可单条忽略、可清空本文件重新分析。

### 5.5 两层解释

- 第一层（卡片）：1–3 句，说清「它在这一页里是什么意思、为什么出现」；提示词明确要求不要写成教科书段落。
- 第二层（深入理解）：点击后带着**这条建议引用的那段原文**打开 AI 助手，以「逐步讲解」模式提问。实测请求的选中段落正是那条引文（49 字）。

### 5.6 实测

| 检查                       | 结果                                                    |
| -------------------------- | ------------------------------------------------------- |
| 启用前                     | 请求数 0                                                |
| 启用后                     | 只请求当前页（153 字）                                  |
| 标记                       | 3 个，都落在被引用的文字下沿（命中区宽 384px 的整行）    |
| 伪造引文                   | mock 故意混入 1 条不在原文里的引文，服务端丢弃，未成标记 |
| 卡片                       | 先给通俗解释，并声明是 AI 输出                          |
| 深入理解                   | 带着 49 字原文提问                                      |
| 忽略一条                   | 标记 3 → 2                                              |
| 隐藏标记                   | 页面上 0 个标记，列表仍保留建议                         |
| 刷新                       | 分析请求总数仍为 1，标记从缓存回到原位                  |
| 换一个 PDF                 | 上一个文件的标记 id 在新页面上不存在                    |

## 六、Task D：AI 交互与安全

- 仍然复用 Phase 4.2 的本地服务：Key 不进前端、只监听回环、两个既有接口 + 新增的 `/api/ai/difficulties`（同样受来源校验、Host 校验、请求体上限、频率与并发限制）。
- 难点分析的系统消息是常量，页面正文只在 `<paper_text>` 数据块里；**「系统消息与论文内容无关」这条不变量有测试**（至少三处：问答、页范围、难点）。
- 模型输出仍走 Phase 4.2 的边界：正文纯文本 + 引用块 JSON；难点输出是独立的小 JSON，形状不对即 `malformed`，不显示原始 JSON。
- 有效引用仍逐字校验；难点引文同样逐字校验。
- **没有自动调用**：应用启动、刷新、导入都不调用；难点分析在启用后才按阅读位置进行；「深入理解」是读者点击触发的。
- 本轮施工与验收只用了 Mock Provider——**除第二节那 2 次事故调用**。

## 八、本轮发现并修复的缺陷

### 8.1 阅读位置在列宽变化时丢失（产品缺陷，新功能带出来的）

侧栏打开/收起会改变 fit-width 比例，每一页的高度随之改变，而滚动偏移是像素值——它会原地不动，读者于是落在别的地方。修复：以「页 + 页内比例」为锚点，比例变化后用新布局恢复。

### 8.2 每次重着色都触发 Canvas 读取警告（产品缺陷）

直接对可见画布 `getImageData` 会让 Chromium 每页警告一次 `willReadFrequently`。改为在独立工作画布上读取与回写。

### 8.3 验收脚本让页面绕过离线服务（事故根因，见第二节）

预览服务器没传 `AI_PORT`，代理默认指向 8787。已修复，并加了经过代理的身份校验。

### 8.4 对比度审计把「被裁掉的文字」算进去了（工具缺陷）

侧栏底部有一行文字被滚动裁切，审计仍按完整矩形取样，把面板外的像素当成背景，报出 1.19:1 的假失败。修复：取样区域先与所有可滚动祖先的边界求交，完全不可见的跳过。**修复后测得的文本片段从 73 降到 59**——两次数字不能直接比较。

### 8.5 Playwright 的 `name` 默认是子串匹配（测试缺陷，但很值得记）

项目名「沉浸式**阅读**验收」包含「阅读」，于是 `getByRole('button', { name: '阅读' })` 先命中了侧栏的项目按钮，而不是论文行里的「阅读」。表现为「点开阅读器毫无反应」。已全部改为精确匹配。

### 8.6 `verify:reader` 里有一条断言旧的「深色下纸仍是白的」（契约变更）

Phase 5 有意改变该行为。已改为两条：深色下纸张跟随阅读模式；切到「原始」后仍是白纸。

## 九、未解决的限制

1. **新输出协议仍未经过真实模型验证。** Phase 4.2 的 `<<<CITATIONS>>>` 协议，以及本轮的难点 JSON 协议，都只在 mock 上验证过。真实模型是否遵守、难点分析的质量如何，需要一次显式授权的联调——本轮明确禁止（除事故）。
2. **灰度图像会被当成墨。** 见 3.1。整页图像密集时会被 35% 规则拦下并回退；单张灰度图没有拦截，只能靠「原始」模式。
3. **深色纸上的深色彩色文字**（例如深蓝链接）保持原色，可能对比度不足。本轮的测试纸没有覆盖这类页面。
4. **难点分析是按页、按需的**：只分析读者停留过的页；不给整篇论文出总览。
5. **Mock 分析器是确定性的浅层实现**（取长句当引文），它验证的是「分析 → 校验 → 定位 → 标记 → 缓存」这条链路，不验证识别质量。
6. **费用估算**：难点分析每次一页，成本取决于页长与模型；本轮没有真实数据。
7. **窄视口**（<1100px）下面板是覆盖式的，轨道按钮可能压住页面右边缘几个像素。
8. **事故遗留**：那个付费 DeepSeek 服务仍开在 8787，建议停掉。
