## 三、每项问题的处理方式与理由

### 3.1 A1 —— 旧 id 不再当作身份证明

**规则**：同一旧 id 下的记录，只有**元数据完全一致**（标题、作者数组、年份都相等）才视为同一篇论文。不一致时按"第几条不同记录"拆成多篇：第一条保留原 id，其余用派生 id `原id#序号`。

**理由**：旧 id 是项目局部标识，`crypto.randomUUID()` 保证了本应用的 id 全局唯一，但它只被当作"记录标识"用过，从未被当作"论文身份"使用过。两条记录共享它、内容却不同，说明 id 被复用（复制/编辑），此时合并会**静默删掉一篇论文的元数据**并把两个项目都指向幸存的那一条——这是不可逆的错误，而拆开只是多一条记录，用户可以自己合并。符合"对无法可靠确认的身份关系必须保守"。

**确定性与可复现性**：拆分只看（旧 id、该记录在其中的出现次序），遍历顺序固定为"项目数组顺序 → 核心论文 → 关联论文顺序"，因此同一载荷每次都得到同样的 id。实测：同一载荷两次迁移结果 `toStrictEqual`；迁移输出再迁移结果不变。

**正常数据不受影响**（实测）：id 不重复的载荷走 `takePaperId(id, 0, …)`，与修复前逐字节一致；同一篇论文被多条记录引用且元数据一致时，仍然只登记一条。

**A2 的处理**：`takePaperId()` 在两条路径上都循环到一个空位，所以普通 id 与派生 id 撞车时后者让位（`shared#1` → `shared#1#`）。谁让位由遍历顺序固定，结果仍然确定。副作用是"先到先得"，即一条派生 id 可能先占掉后来出现的同名字面 id；这一点由测试断言"三个 id 互不相同、三篇论文都在、每个引用都能解析"来守住，而不是断言某个具体字符串。

### 3.2 B1 —— 外部标识冲突显式返回，不猜

**接口**：`resolvePaperIdentity(papers, ids)` 返回结构化结果：

- `{ kind: 'none' }`：没有可用标识 → 绝不自动匹配（标题不参与）。
- `{ kind: 'match', paper }`：所有可用标识指向同一篇（含"两个标识都指向它"和"只有一个标识能对应上"）。
- `{ kind: 'conflict', papers }`：标识之间不一致，或同一个标识在注册表里对应多篇（注册表自身不一致）。**按插入顺序返回涉及的论文，不排序、不挑赢家。**

`referencePaper()` 对应返回 `{ status: 'linked' | 'conflict' | 'invalid' }`；`conflict` 时**不新建、不挂链、不落盘**（实测：dispatch 一次都没发生，快照对象引用未变）。

**理由**：DOI 优先是一条隐含策略，会把"A 的 DOI + B 的 arXiv"这种输入静默变成"A 的论文"，用户看不到任何异常，只会发现笔记挂错了论文。合并 A、B 更糟——那等于编造一条数据不支持的等价关系。把冲突显式抛给调用方，配合本轮的界面提示原则，用户或上层功能才有机会决定。

**删除了旧接口**：`findPaperByExternalId` 被 `resolvePaperIdentity` 取代，没有保留"DOI 优先"的辅助函数——留着它，未来调用方还会踩同一个坑。

**情形 4（补充标识 / 修正元数据）**：当前没有任何接口会改写已登记论文的字段，`Paper.id` 生成后不再重算，`withPaper()` 拒绝覆盖已登记条目。因此"补充 DOI/arXiv 或修正元数据"不会改变稳定 id，也不会破坏引用——这一条**由构造保证**，并已补行为验证（见第二节"只补验证"）。本轮**没有**实现论文元数据更新接口：没有消费者，且一旦实现就必须同时定义"已有标识与新标识冲突"的合并规则，属于 Phase 2 的工作。

### 3.3 C1 —— 加载失败必须让用户看到

新增只读提示，四种原因各有措辞，都说明"数据仍在本机、没有被删除/覆盖"以及"确认恢复前不要清理浏览器数据"：

| 原因                  | 提示要点                                                                 |
| --------------------- | ------------------------------------------------------------------------ |
| `unreadable`          | 数据已损坏无法读取；原件保留在本机（隔离副本 `rw.projects.corrupt`）     |
| `invalid`             | 数据格式不正确无法读取；原件保留在本机（隔离副本 `rw.projects.corrupt`） |
| `unsupported-version` | 由更新版本的应用写入，当前版本读不了；已完整备份（`rw.projects.backup`） |
| `migration-failed`    | 升级失败并已停用该数据；已完整备份（`rw.projects.backup`）               |

**决策与理由**：

- **复用 `.banner` 与 `role="status"`，不改任何 CSS**（本轮 CSS 体积 16.46 kB 与 Phase 1 完全相同）。这样正常场景的渲染零变化，12 张截图仍与 Git 基线一致。
- **把存储键名写进提示**。这看起来偏技术，但没有键名用户根本无法找回数据，"数据还在"就成了一句空话。提示里**不含**原始 JSON、堆栈或任何内部错误信息——有专门测试断言页面上既没有 `{oops` 也没有 `SyntaxError` 之类的字样。
- **没有做"重新开始"按钮**：任务书说本轮不要求数据恢复管理器。现在不会用空状态覆盖原件（见 3.4），也没有任何一键清除入口。
- **失败时应用仍可用**：实测可以在空状态里正常新建项目并打开项目页。

### 3.4 C2 / C3 —— 恢复副本不再被静默覆盖

**策略（三行规则）**：

1. **写 live 键之前，必须先把原件复制到隔离区**（`keepCopy`）。
2. **隔离区永不覆盖**：每一族只有 3 个槽位（`rw.projects.corrupt`、`.2`、`.3`；备份族同理）。槽位里已有**不同**内容就换下一个空位；已存在**相同**内容则什么都不写。3 个槽位都被不同内容占满 → 报告复制失败。这样既不覆盖旧副本，也不会无上限占用 LocalStorage（实测 6 次连续不同故障后，隔离键始终只有 3 个，且**最老的那份存活**——最老的更可能是用户最后一次良好的状态）。
3. **复制失败就不写 live 键**：`LoadResult.recoveryCopy` 变成 `failed`，`persisted` 为 `false`；Store 记录这个状态，本会话只做内存更新、**完全跳过落盘**，直到用户重载且复制成功（例如腾出空间）为止。迁移路径同理：原件复制不了就**放弃升级**，v1 载荷原地不动（实测 `persisted: false`、live 键仍是 v1 原文）。

**理由**：`rw.projects` 是唯一被应用持续写入的位置。只要"覆盖它之前先确保有副本"这条不变量成立，任何后续写入都不可能销毁唯一可恢复的副本。这是最小实现，没有引入备份管理器或版本化存储。

**界面表现**（实测，见 5.3）：复制成功时只显示一条加载失败提示，应用照常可用并可正常保存；复制失败时两条提示同时出现（加载失败 + "浏览器没有保存最近的改动"），如实反映"能看不能存"。

## 八、仍未解决的限制

1. **没有数据恢复工具**。用户可以"看到"数据被隔离以及隔离键名，但没有任何界面能导回或导出它；恢复需要开发者工具或后续版本。这是本轮的明确边界（任务书也不要求）。
2. **论文元数据更新接口不存在**。补充 DOI/arXiv 或修正标题目前无法完成；实现时必须同时定义标识冲突规则（与本轮 B1 同一类问题）。Phase 2 的第一件事。
3. **PDF 内容哈希身份未实现**。`Paper` 与 `resolvePaperIdentity()` 是它的接入点，但哈希匹配、同哈希不同文件的判定都还没写。
4. **进程级重启未验证**（无桌面壳）。
5. **Tauri 壳未接入**（本轮范围外）。
6. **配额耗尽的真实压测缺失**：C2/C3 的保护用内存桩模拟写入失败验证过，没有在真实满配额环境里跑过。
7. **`updatedAt` 一字段两用、作者稳定标识**等 Phase 0 遗留项仍未处理（与本轮无关）。
8. **迁移的"先到先得"**：A2 场景下谁让位取决于遍历顺序。结果确定且无数据丢失，但若将来希望"字面 id 优先于派生 id"，需要改成两遍扫描。
9. **Git 身份是仓库本地占位值**（`user@localhost`）。如果将来的提交要对外署真名/邮箱，请自行改 `git config user.email`。

## 九、Agent 执行过程中的有效工作与重复操作

口径说明：拿不到 token 用量与账单数据，下面**不含任何 token 或费用估算**，只描述可观察的工作构成。本轮未调用任何其他 AI 模型或子代理。

**有效开发**：修改 6 个源文件（迁移身份规则、外部标识解析接口、隔离/保护策略、写入锁、失败提示），新增 1 个测试文件、扩充 5 个测试文件（+36 项）。核心设计只有四个决定：按元数据指纹而非 id 归并、冲突显式返回而非挑选赢家、覆盖前必须先有副本、复制不了就不写。

**测试与验证**：4 次局部 `vitest`（domain/services/features 分批）+ 1 次全量 + 1 次 `npm run check` + 1 次 `npm run build` + 1 次 `npm run verify` + 3 个浏览器故障场景 + 1 次逐文件项数统计。

**修复**：1 轮测试失败（2 项，都是**我自己写错的断言**，不是实现缺陷：一个断言了拆分后的具体 id 字符串、一个断言了两次加载结果对象完全相等，而 `recoveryCopy` 在两次加载间天然不同）；1 次 Prettier 格式修正（5 个文件）。另外在写测试阶段主动发现并修掉了自己引入的 A2 撞车缺陷（在跑测试之前）。

**重复操作（如实列出）**：

1. 在本轮开始前重跑了一次全量测试确认基线（约 37 秒）。这是任务书要求的"不得未经核实直接宣称当前仍然通过"，属于必要成本，不是浪费。
2. 浏览器点击两次因 "layout metrics unavailable" 失败，按提示先截图再点击即成功。这类往返在预览面板刚打开时会稳定出现。
3. 一次报告文件的行数统计（`grep -v "lf/lf"`）写法有误，多跑了一条命令才拿到正确的换行统计。

**可以省下但没省的部分**：完整跑了 `npm run verify`（而不是只跑故障场景）。理由：本轮动了持久化的写入路径，而 verify 里"刷新后 7 个项目仍在"正是写路径的端到端证据；同时 12 张截图的 `git status` 干净一次性证明了界面零回归，比逐场景抽查便宜。

**没有做的事**：没有通读全工程、没有为凑数加断言、没有引入新依赖、没有在通过后再发起额外审计。
