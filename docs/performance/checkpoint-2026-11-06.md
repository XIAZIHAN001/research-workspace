## 测量方法与代价

同一 Linux / Node 24.22.1 环境，按基线再候选顺序运行；每个操作 2 次预热、7 次采样。下表为毫秒；p95 在 7 个样本下就是最大值，噪声较大。输入构造、编译和正确性比对不计入耗时，冷查询包含索引建立，热查询复用同一索引。详见 [复现说明](README.md)、[完整基线](baseline-2536305.json)、[完整候选](candidate-533b9ff.json)。

这些是合成 Node 算法测量，不是浏览器输入延迟、PDF.js 真文件抽取时间、端到端导入速度或 Windows WebView2 数据；不能直接据此承诺 UI 提速倍数。

收益与限制同时保留：

- 1 万记录高命中热搜索 21.111 → 0.665 ms；但无命中冷查询 4.246 → 23.356 ms，CJK 冷查询 6.592 → 15.216 ms。索引在搜索框打开时建立，不能声称打开对话框更快。该取舍换取后续连续查询更低成本。
- 1 万篇库中的 500 项身份解析/新记录批次 1454.632 → 9.107 ms。该基准不含真实持久化与 UI 渲染。
- 200 页混合 PDF 热查询序列 76.200 → 0.349 ms；1000 页超出折叠缓存的热查询仅 375.758 → 295.089 ms，冷序列 350.242 → 355.348 ms，未宣称所有大文档路径都更快。
- 索引以保留数据换取重复计算减少。1 万记录索引构造观察到约 6.98 MB 的 GC 后堆差；此值不是峰值或严格增量界限，其他进程活动和对象生命周期会影响它。热查询的近零/负堆差不表示缓存不占内存。
- 当前共享页提取最多保留前面适合预算的 128 页 / 200 万字符；折叠搜索最多 256 页 / 200 万字符；跨重开 transcript 最多 4 份、合计 200 万字符、每份 2048 个有文本的页面。超出预算仍完整搜索，但会重新抽取或折叠，后部页面的重复知识分析不保证命中缓存。
- 已开始的 PDF.js 提取不能由单个消费者强制取消；关闭/替换会停止该消费者的后续任务和状态写入，不会取消其他消费者仍需的共享任务。

## 已修复的复审问题

- 大文档搜索框关闭再打开曾忽略仍在内存中的完整索引，200 页会再次抽取。现复用成功索引，部分失败仍可重试。
- FIFO 页缓存曾在 129 页顺序重扫时产生 258 次抽取。改为稳定有界准入后，相同两遍扫描为 130 次；没有通过扩大到无界缓存掩盖问题。
- 保留同 SHA 文件重开复用，200 页场景有覆盖；全局 transcript 不保存 PDFDocumentProxy。
- 飞行中替换文档的旧完成分别在新完成之前/之后到达均有直接测试，旧结果不写入新文档。

## 未完成与明确延后

- 全量 PDF 组件窗口化、离屏页尺寸调度和混合页锚点重构未实施；当前仍保留 O(P) 页槽和原测量流程。本轮仅优化滚动事件中的页查找。
- 持久化架构、整工作区同步写入及相关数据迁移未改。需要另行专项测量及恢复/强退验收，不把普通编辑异步化当作无风险提速。
- 本云容器此前的 Chromium 启动受 socket 权限限制，本轮未用设置绕过；新的真实浏览器验收等待该发布提交的官方 CI。Windows 普通权限/WebView2/安装运行阻塞仍独立保留，不能用本轮 Linux 结果替代。
- 基准比较器目前验证完整输出，却不自动拒绝不同 provenance 的报告。本次已独立核对 harness、lockfile、环境和采样设置相同；自动拒绝不一致报告是后续的小型工具加固项。
