## 三、数据模型：Schema v3

### 3.1 新增字段

| 对象    | 新增                                                                                         |
| ------- | -------------------------------------------------------------------------------------------- |
| `Paper` | `pdf?: { sha256, name, bytes, pageCount, addedAt }` —— 本地 PDF 的**元数据**（字节不在这里） |
| `Paper` | `reading?: { page, updatedAt }` —— 阅读位置，只有页码                                        |
| 状态    | 顶层 `version` 从 2 升到 3                                                                   |

**为什么升版本**：两个字段都是可选的，v2 载荷本身就是合法的 v3 载荷；但版本号一变，旧构建会明确拒绝（进 `.backup`、不改写 live 键），而不是在下次写入时静默丢掉 PDF 绑定。2→3 的迁移只做"先校验、再改版本号"，不改任何数据。

**为什么阅读位置只存页码**：像素偏移随缩放和窗口大小失效，DOM 节点更是短命。将来的段落级锚点必须由 PDF 自己的文本内容导出（例如"第 N 页第 k 个文本项"），而不是渲染出来的元素——`reading` 是给它留的位置，本轮不实现。

### 3.2 字节存放：LocalStorage 与 IndexedDB 的写入顺序

PDF 字节**从不进 LocalStorage**。它们存在 IndexedDB 里，键就是 SHA-256 内容哈希（内容寻址 → 同一个文件天然只占一份）。两个存储之间没有事务，所以顺序被固定成：

```
读字节 → 结构校验（%PDF- 魔数、大小上限）→ SHA-256 → 用 pdf.js 真解析一次（校验 + 取页数）
   → 写 IndexedDB（已有同哈希则跳过）→ 才允许往论文注册表写引用
```

任何一步失败或中断，最坏只留下一个**没人引用的 blob**，绝不会出现"论文指向一个从未保存成功的文件"。反过来（注册表先写、blob 后写）会出现悬空引用，所以不这么做。

读取时若 blob 不见了（用户清理过浏览器数据），阅读器给出明确提示并提供重新导入入口（实测，见第五节）。

### 3.3 内容哈希 ≠ 学术身份

这一条被单独实现并实测：同一个文件第二次导入时，对话框**不会**自动合并，而是问用户：

> 这个文件和《X》用的是同一份文件（内容哈希相同）。同一份文件不代表同一篇论文。
> [ 仍然新建一篇论文 ] [ 加入《X》 ]

DOI / arXiv 的身份判定仍走 Phase 1.1 的 `resolvePaperIdentity`：两个标识指向不同论文时给出 `conflict`，**一个字节都不写**。

### 3.4 四种操作语义分开

| 操作             | 入口                                     | 写入的动作                                            |
| ---------------- | ---------------------------------------- | ----------------------------------------------------- |
| 导入新论文       | 项目页「导入新论文」/ 论文库「导入论文」 | `referencePaper`（识别或新建）或 `addPaper`（仅入库） |
| 给已有论文补 PDF | 论文行「导入 PDF」/「替换 PDF」          | `updatePaper({ pdf })`，不碰身份                      |
| 从论文库关联     | 论文库每行的项目选择器                   | `linkPaper`，只加引用                                 |
| 修改论文信息     | 论文行「编辑」                           | `updatePaper({ title/authors/year/doi/arxivId })`     |

改元数据时，如果输入的 DOI / arXiv 已经属于**另一篇**论文，整个编辑被拒绝并说明归属（实测 + 单测），既不合并也不覆盖别人的身份。

## 四、阅读器

- **渲染**：`pdfjs-dist@6.4.299`，通过 `import()` 懒加载（正常界面从不加载它），worker 与标准字体/CMap 数据都由 Vite 从**本地安装的包**产出为本站资源（新增 `vite.config.ts` 里的一个插件），**不依赖 CDN**。
- **页面管理**：连续滚动的一列页面，只渲染可见页 ±1（`renderWindow`），离开窗口就释放 canvas 与文本层；300 页的论文打开时只付一页的渲染成本。
- **定位**：`scrollTop` → 页码用纯函数 `pageAtOffset` 计算，带 2px 容差（`scrollTo` 会落在小数像素上）。
- **文本层**：用 pdf.js 自己的 `TextLayer`，样式按包内 CSS 自行实现最小子集（没有引入整套 viewer 样式）；选中与复制是浏览器原生行为（实测选中文本可以读出来）。
- **稳定性**：单页渲染失败只在该页显示一行提示；整个阅读器外面套了 `ReaderBoundary`，即使阅读器抛出未预期错误，工作区其余部分不会被卸载（单测 + 实测的"文件丢失"路径）。
- **位置持久化**：页码变化后 800ms 去抖写入；跳页动画期间的中间位置被忽略，避免把路过的一页当成"上次读到这里"。

## 六、本轮发现并修复的真实缺陷

| #   | 缺陷                                                                                                  | 如何发现                                                                       | 处理                                                                                         |
| --- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| 1   | **pdf.js 会转移（detach）传入的 buffer**：校验用的解析会把待写入的字节清空，导致保存出一份 0 字节文件 | 读 pdf.js 源码（`sendWithPromise("GetDocRequest", docParams, [data.buffer])`） | 校验时传副本；并写了一个**真的把 buffer 转移掉**的回归测试，断言哈希、字节数与正文都不受影响 |
| 2   | pdf.js 6 的 `PDFDocumentProxy` 没有 `destroy()`，文档资源由 loading task 持有                         | `tsc` 报错                                                                     | 打开文档时一并返回 `close()`，读取与校验两条路径都正确释放                                   |
| 3   | pdf.js 6 的 `page.render()` 要求传 `canvas`（只传 `canvasContext` 会被忽略）                          | `tsc` 报错                                                                     | 由 effect 自己创建 canvas 交给 pdf.js，同时避开"同一 canvas 并发渲染"限制                    |

| 5   | 跳页的平滑滚动期间，页码指示器会闪回中间页，且可能把中间页写成"上次读到"                              | **浏览器验收**（加了滚动轨迹追踪）                                             | 跳页期间忽略非目标页码的滚动事件；新增检查断言指示器不闪回                                   |
| 6   | `usePdfDocument` 在 effect 体内同步 `setState`，被 react-hooks v7 判定为级联渲染                      | `eslint`                                                                       | 改为从"当前打开的是哪个哈希"派生状态                                                         |

## 八、未验证与遗留问题

**未验证（没有证据，不当成已完成）**：

1. **没有用真实论文 PDF 验证过**。样本是我生成的 3 页、用标准字体、无图片的 PDF。真实论文（嵌入字体、图表、扫描页、几十上百页）没有跑过——尤其扫描件（无文本层，选不中）和 CJK 非嵌入字体（走 CMap 路径，代码已配置但未实测）。
2. **大文件未验证**：整份 PDF 一次性读入内存交给 pdf.js（`data` 模式，没有分块/range 请求）。几十 MB 应该没问题，但数百 MB 的行为没有测量。
3. **浏览器进程级重启后的持久性未验证**：只验证了刷新（重开页面）后文件与位置都在。IndexedDB 本身是持久存储，但没有跨进程重启的实测（没有桌面壳）。
4. **只在 Edge 上验证**（与本项目既有验收口径一致）。
5. **加密 PDF 只有"拒绝"路径**：pdf.js 的 `PasswordException` 会落到"无法解析这个 PDF"的提示里，没有单独的密码输入界面。

**遗留（本轮范围外，已记录）**：

6. **PDF 文件没有删除/回收**：换文件或删论文后，旧的 blob 仍留在 IndexedDB（内容寻址，不会重复占空间，但也不会自动清理）。需要一个"存储用量 + 清理"入口。
7. **没有批注/段落锚点**：`reading.page` 是页级锚点；段落级锚点应基于 PDF 文本项，Schema 有扩展空间（走 3→4 迁移）。
8. **论文库没有分页/筛选**：几百篇以内没问题，上千篇需要虚拟列表。
9. **Tauri 仍未接入**：桌面壳接进来时，PDF 字节应该落到文件系统而不是 IndexedDB，这会影响 `PdfBlobStore` 的实现（接口已经隔离好，但 `pdf` 记录的 `sha256` 语义要重新确认）。
10. **OCR / 全文检索 / AI 摘要 / 知识图谱**：本轮未做，也不在下一轮的默认范围内。

## 九、执行效率复盘

口径：拿不到 token 用量与账单数据，下面**不含任何 token 或费用估算**，只描述可观察的工作构成。本轮未调用任何其他 AI 模型或子代理。

**有效开发**：新增 26 个源文件（领域 3、导入与论文库 6、阅读器 7、样式 2、测试 8），修改 13 个既有文件。核心设计决策只有三个：字节走 IndexedDB 且以内容哈希为键、写入顺序固定为"先 blob 后引用"、身份与内容哈希彻底分开。

**测试与验收**：全量单测在几个关键节点各跑一次（数据层、UI 接线、阅读器修复后）；`npm run check` 与 `npm run build` 每个节点各一次；`npm run verify` 跑 2 次（改动前后各一次，都是 61/61）；`npm run verify:reader` **6 轮**（第 1 轮 2 项失败 → 第 6 轮 26/26）。浏览器验收是这一轮最有价值的部分——**6 条真实缺陷里有 2 条只有它能发现**（恢复时机、跳页闪烁），另一条（buffer 转移）是读库源码发现的。

**重复与无效操作（如实列出）**：

1. 三次为了"看清现象"写的临时诊断（滚动轨迹、几何包围盒、画布像素取样）——其中两项后来保留为正式检查（布局可见性、画布有墨迹），一项（滚动轨迹）被更强的断言取代。这部分是必要的，不是浪费。
2. 截图定位错误导致我第一次拿到的"阅读器截图"是空白的。实际上页面渲染是好的（画布取样有 225 个暗像素），只是缩放 179% 时视口停在了页面之间的空白处。为此多跑了一轮验收。
3. `npm run verify` 会覆盖 `docs/screenshots/`，我每次都要从 git 恢复——这个"跑完记得还原"的动作重复了两次。已记录在案：如果 Phase 3 还要频繁跑，应该给它加一个输出目录参数。
4. 脚本里的死代码（一个写了一半的 `importPdf` 辅助函数）直到 `eslint` 报 `no-unused-vars` 才发现。

**没有做的事**：没有通读整个工程，没有为凑数写断言，没有引入阅读器框架（只用 pdfjs-dist + 自己的 200 行渲染层），没有为了让验收变绿而放宽任何既有断言。
