## 一、结论

1. **先盘点，再动手。** 在写任何导出代码之前，先按源码逐个确认了应用实际保存的每一个键、每一个对象仓库、它们之间的引用，以及哪些内容可以由算法重新生成（第二节）。这份清单直接决定了备份里放什么、不放什么。
2. **整个知识库是一个文件。** 版本化的 JSON 头 + 按内容哈希去重的 PDF 字节；两个论文共用同一份 PDF 时只打包一次。备份里没有任何 Key、环境变量或令牌。
3. **恢复是五步，不是一步。** 检查 → 预览 → 用户确认 → 执行 → 回读验证；检查阶段不写任何东西。写入前在 IndexedDB 留下恢复日志，任何一步失败都会把已经写入的键还原。
4. **身份从不按标题决定。** 同 id 同内容直接跳过；同 id 不同内容默认保留本机，并要求读者显式选择；DOI/arXiv 相同的两篇论文会并入已有记录并重写全部引用；同名项目只是两个项目。
5. **跨项目复用成了完整功能。** 概念可以被加入另一个项目、从某个项目移出、点开它所属的每个项目；移出只改变它出现在哪里，不删概念、出处或笔记。
6. **真实论文验证不是演示。** 两篇 CC-BY 论文（扩散语言模型 / 时间序列语言模型）里，7 个概念、7 条前置关系、7 处逐字出处全部通过界面手工建立；`语言模型` 在两篇论文里各有一条不同的引文，两条依赖链都是三层深；一个无出处概念被明确标成「尚无出处」；替换 PDF 后旧出处保留但拒绝跳转。
7. 回归：`check` **52 文件 / 1185 项**、`build`、`verify:backup` **39 项（新）**、`verify:knowledge-real` **16 项（新）**、`verify:graph` 17、`verify:guard` 10、`verify:ai` 54、`verify:immersive` 33、`verify:real` 28、`verify:annotations` 26、`verify:reader` 27，全绿。

### 2.2 引用关系

- `Project.corePaperId` / `relatedPaperIds` → `Paper.id`；
- `Paper.pdf.sha256` → `rw.pdfs/files` 的键；
- `Annotation.paperId` → `Paper.id`；`Annotation.pdfSha256` 是画这条高亮时的文件；
- `ConceptEvidence.conceptId` → `Concept.id`；`paperId` → `Paper.id`；`pdfSha256` 决定它还能不能跳回原文；`annotationId` / `suggestionId` 指回来源；
- `ConceptRelation.from` / `to` → `Concept.id`；
- `Concept.projectIds` → `Project.id`；
- 难点缓存记录的 `paperId` / `pdfSha256` 也指向论文与文件，但这份数据丢了可以重算。

**共用的身份**：同一个 `Paper.id` 被项目、批注和出处同时引用；同一个文件哈希可以被**多个论文**引用（本轮浏览器验收专门构造了两篇论文共享一个 PDF，导出后只打包一次）。PDF 哈希在所有引用点上保持一致：文件内容决定哈希，哈希决定存储键，论文绑定记的也是它。

### 2.3 哪些能重建，哪些不能

- **不能重建**：项目、论文元数据、批注与笔记、阅读位置、概念、关系、出处、恢复副本、头像。
- **可以重建**：难点分析缓存（一旦丢失，只是需要重新分析；但「忽略过哪些建议」属于用户意图，所以随缓存一起导出，并在合并时取并集）。
- **严格迁移**：`rw.projects` 走完整的 1→5 迁移链；`rw.knowledge` 在**恢复时**使用严格解析（任一引用不成立即拒绝整份备份），日常加载仍保留原来的宽容策略与隔离副本。

## 三、Task B：备份格式与恢复

### 3.1 容器格式（`.rwbackup`，格式版本 1）

```
偏移 0   "RWBACKUP"（8 字节）
偏移 8   uint32 LE  头部长度
偏移 12  uint32 LE  载荷长度
偏移 16  JSON 头（UTF-8）
之后     各 PDF 原始字节，按头里的 offset 顺序排列
```

头部包含：格式名与版本、创建时间、应用与两份数据的 schema 版本、各类对象数量、**数据区**（项目/论文/批注、知识、难点缓存、偏好、恢复副本、导出时已缺失的文件哈希）、文件表（sha256、原始文件名、字节数、偏移）、以及数据区的 SHA-256。

- 完整性有两层：每个文件按内容哈希校验；数据区用**规范化 JSON**（键排序）计算摘要，避免键顺序变化导致合法备份验不过。
- 版本不猜：`formatVersion > 1` 直接拒绝并说明「由更新版本写入」。
- **不使用 ZIP**：PDF 本身已压缩，JSON 很小；不引入解压器就没有解压炸弹这种攻击面，也不增加第三方解析依赖。浏览器可以把 PDF 的 Blob 直接拼进输出，峰值内存只有一个 PDF，而不是整个备份。

### 3.2 检查阶段（不写任何东西）

`inspectBackupFile` 依次核对：帧结构与长度、magic、格式版本、头部形状、文件表（数量、哈希格式、偏移连续、总量）、数据区摘要、项目数据的迁移链、知识引用的完整性（概念→项目、出处→论文、关系两端）、偏好与恢复副本的边界，然后逐个读取 PDF 校验哈希与 `%PDF-` 签名（一次一个文件，读完即释放）。

之后计算：新增数量、同 id 冲突（按身份/决策字段比较，**不看时间戳与阅读进度**）、DOI/arXiv 合并、缺失 PDF、需复制的字节数、按 `navigator.storage.estimate()` 估算的空间是否够（要求不超过可用空间的 80%）。

### 3.3 合并规则

| 情形                                                   | 结果                                                                                      |
| ------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| id 相同、身份/决策字段相同                             | 跳过（重复导入因此是幂等的）                                                              |
| id 相同、内容不同                                      | 默认保留本机；界面要求读者显式选一边（本机 / 备份），未选前「开始恢复」不可用              |
| id 不同、DOI 或 arXiv 相同                             | 并入已有论文：补上它缺的 PDF，项目/批注/出处的引用改写到已有 id；已有元数据不被覆盖         |
| 项目同名但 id 不同                                     | 作为另一个项目导入，**绝不按名字合并**                                                    |
| 概念的项目链接                                         | 只保留指向本次合并后仍存在的项目；概念本身永不丢弃                                        |
| 关系形成循环依赖                                       | 跳过该关系并说明                                                                          |
| 难点缓存                                               | 按页合并，保留本机结果；忽略列表取并集                                                    |
| 偏好                                                   | 只填本机缺失的项；本机已有的一律不覆盖                                                    |

### 3.4 执行阶段与失败保护

1. 计算合并结果与**确切的写入集合**（内容相同的键不写）；
2. 把每个键的旧值与新值摘要写入 IndexedDB 的恢复日志——日志写不成，就一个字节都不写；
3. 先复制 PDF（内容寻址、只增不改，失败最多留下孤立 blob，不会破坏任何论文）；
4. 再逐个写 LocalStorage 键；
5. 从存储**回读**每个键（哈希一致）、重新解析项目与知识、核对数量、确认本次应写的 PDF 都在，才报告成功；
6. 任一环节失败：把写过的键按日志还原；还原成功则清日志；还原不了就留着日志，下次启动继续处理。

启动时 `recoverInterruptedRestore` 在创建任何 store 之前运行，区分三种情况：所有键已是新值（恢复其实完成了）→ 清理；所有键仍是旧值（没开始）→ 清理；混合（写到一半）→ 写回旧值。`reader` 回归暴露的一个问题也在这里修掉：浏览器禁用 IndexedDB 时，日志工厂不能再让应用白屏。

### 3.5 资源与安全边界

| 限制           | 值                                     |
| -------------- | -------------------------------------- |
| 头部 JSON      | ≤ 32 MB                                |
| 文件数量       | ≤ 512                                  |
| 单个文件       | ≤ 200 MB（与 PDF 导入上限一致）        |
| 载荷总量       | ≤ 2 GB                                 |
| 恢复副本       | 单项 ≤ 8 MB，合计 ≤ 16 MB              |
| 头像           | 只接受 `data:image/(png\|jpeg\|webp\|svg+xml);base64,`，≤ 2.8M 字符 |

- 备份包里的任何内容都不会被当作脚本或 HTML 执行；文件名只作为文本显示，控制字符被去掉；PDF 走与手动导入相同的魔数检查。
- 不访问网络、不上传论文；导出的文件权限由用户自己的文件系统决定（格式 v1 不加密，这是已知限制）。
- 恢复不删除任何既有对象；唯一会消失的是「读者显式选择用备份版本替换」的那些同 id 对象。

## 九、本轮发现并修复的缺陷

1. **冲突的单选按钮默认已选中，读者无法做出「显式选择」**：按钮仍被禁用，但界面看起来已经选过。修复：有冲突时两个选项都不预选，点过任意一个才允许恢复。
2. **缺 PDF 的确认勾选没有写进恢复选项**：按钮变可用，执行时仍被拒绝。修复：勾选同时设置 `importMissingPdfs`。
3. **禁用 IndexedDB 的环境整个应用白屏**（`verify:reader` 回归发现）：启动时恢复日志的工厂在参数求值阶段抛错，`.catch` 接不住。修复：安全读取 `indexedDB`、启动兜底、日志不可读时按「没有日志」处理（恢复功能本身会拒绝启动并说明）。
4. **读过恢复后的论文，再导入同一份备份却被要求选择冲突**：冲突比较把阅读位置和更新时间算进了内容。修复：只比较身份与读者决策字段；时间戳与阅读进度不构成冲突。
5. **Phase 6 的「返回后导航状态重置」**：知识视图的模式与选中概念随组件卸载丢失。修复：提升到 App，按项目保留。
6. **验收工具的三处问题**（不是产品缺陷）：真实论文的目标句在第 2/3 页而不是第 1 页；跨行连字符 `understand- ing` 让整句匹配失败（改为取不含该词的子句）；`替换 PDF` 的对话框标题是「导入 PDF 文件」。

## 十、已知限制

1. **没有跨存储事务**：LocalStorage 与 IndexedDB 无法原子提交。恢复日志 + 补偿写入能保证「失败可还原、崩溃下可判断」，但不是数据库意义上的原子性。PDF 复制完成后若在写数据前崩溃，可能留下没有被引用的 blob（无害，本轮不自动清理）。
2. **校验按文件读入内存**：峰值约等于最大的单个 PDF；上限 200 MB/文件、2 GB/包。超出浏览器能力的超大库没有验证。
3. **空间估算依赖浏览器**：不同浏览器对 `estimate()` 的准确度不同；只在「明显不够」时阻止，真正的配额错误靠回滚兜底。
4. **同 id 冲突是整类选择**，不是逐对象选择；对个人知识库的规模足够，但不适合逐条精细合并。
5. **整库恢复，没有「只恢复某个项目」**；恢复副本写入 `.restored` 键后没有专门的查看界面。
6. **备份不加密**：文件里是论文、笔记与知识，请自行保管；格式 v1 没有口令保护。
7. **阅读位置只记页码**，不记页内偏移。
8. **真实知识网络是手工整理的**：本轮不调用模型，也没有自动关系推荐；关联的质量来自读者自己，而不是算法。
9. 图谱仍是静态分层布局（本轮加了缩放与滚动定位，没有拖拽/折叠）；搜索是子串匹配。
10. `rw.sidebar` 这类窗口状态刻意不导出；头像只接受内嵌图片。

## 十三、Agent 执行效率复盘

**有效的部分**

- **先审计再写代码**：把「哪些键、谁引用谁、哪些能重算」写成清单后，备份格式几乎是一次成型的；恢复的合并规则也能直接对应到清单。
- **纯函数先行**：容器编解码、计划与合并、日志三态都用纯函数/可注入依赖实现，28 个领域与格式测试在浏览器端跑之前就已经把边界钉住。
- **用真实产物做端到端**：导出走浏览器的下载事件，导入走文件选择器；没有复制存储目录，也没有伪造成功。
- **反例与正例同等重要**：截断、错版本、冲突、缺文件、写失败都是脚本手工「做坏」一份真实备份再导入，比构造假对象更有说服力。
- **Gate 0 直接复用**：两个新套件都在打开浏览器前校验代理终点与实例 id，全程零 AI 请求。

**代价较高的部分**

- **选择器歧义**：概念名互为子串（`语言模型` / `扩散语言模型`），Playwright 的 `hasText` 会选中更早出现的卡；最后给卡片加了稳定的 `data-concept-name`，测试不再依赖文案。
- **阅读器的滚动时序**：页码跳转用了平滑滚动，1.5 秒内滚动观察器会忽略中间页；测试不得不等待，也让我确认了「证据跳转会把阅读位置改回第 1 页」是产品行为而非缺陷——最终把阅读位置检查放到所有证据跳转之后。
- **真实论文的文本层**：目标句分布在第 1/2/3 页，且跨行连字符会把 `understanding` 拆开；这两点都只在真实 PDF 上暴露，生成样本永远不会遇到。
- **一次回归失败很有价值**：`verify:reader` 在「禁用 IndexedDB」的情境里抓到了启动白屏——这是本轮新增代码带出来的真实缺陷，而不是测试问题。

**总体**：本轮从审计到验收共新增约 6700 行（其中一半以上是测试、验收脚本与报告本身），最后一轮 `check`、构建与全部浏览器套件一次全绿；调试主要集中在选择器与真实 PDF 的文本层，而不是数据层。
