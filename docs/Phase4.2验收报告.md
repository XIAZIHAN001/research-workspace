# Phase 4.2 验收报告：AI 输出可靠性与数学精读体验

日期：2026-10-17。工作目录：`D:\论文阅读解构项目`。分支：`phase4.2-ai-output`（从 Phase 4.1 已验收提交 `b19198f` 建）。

**本轮没有发出任何真实模型调用，费用为 0。** 全部证据来自 mock provider 与保存的历史失败响应回放。

## 一、结论

1. **保存的那条真实失败响应是确定可恢复的。** Phase 4.1 的结论「救不回来」对当时的实现成立，对这条响应不成立：用一条范围很窄、可证明无损的规则可以还原出 2829 字的正文与 7 条引用，且没有猜任何东西。这条规则现在是一个有 6 个用例的测试，回放的是原始字节，不是手写仿制品。
2. **输出协议被简化了，而不是把字符串修复器加固。** 回答正文不再放进 JSON 字符串里——那正是失败的成因。现在正文是纯文本，只有末尾一小块引用信息是 JSON。`response_format: json_object` 随之取消。
3. **解析边界有了明确状态**：`valid` / `recovered` / `malformed` / `incomplete`，加一个只用于失败的 `provider-error`。界面按状态决定说什么，**任何情况下都不把协议文本、JSON 或转义序列显示给读者**。
4. **KaTeX 渲染数学**：`$…$`、`$$…$$`、`\(…\)`、`\[…\]` 都支持，希腊字母、上下标、分式、求和、多行与超宽公式都在真实浏览器里验证过；宽公式在框内滚动，面板宽度溢出 0px。KaTeX 的 HTML 由 KaTeX 自己生成（`trust: false`），模型输出永远不变成标记。
5. **PDF 数学输入的信任边界被量化了**：选段在文字层里是否被拆成单字，现在是一个测得的数字，在发送**之前**显示给读者；界面同时明说「回答里的公式是模型自己排版的，不是从 PDF 里提取的原文」。
6. **离线与在线在机制上分开**：`--offline` 忽略环境里的提供方与密钥；端口被占用就中止，绝不连接已有服务；离线验收套件在真实提供方环境里**拒绝运行**。这三条都在一台**真的跑着付费服务**的机器上验证过（见第七节）。
7. 回归：`check` 1001 项、`build`、`verify:ai` 54 项、`verify:real` 28 项、`verify:annotations` 26 项、`verify:reader` 26 项，全绿。

## 三、任务 A：模型输出的解析边界

### 3.1 先分析保存的真实失败响应

`docs/phase4.1-live-api-formula-report.json` 里那次公式回答，实测结构是：

```
{"answer": "…整段正文…$P_1$ 平滑地移向高 $R$ 的区域。\", \"groundedInText\": true, \"citations\": [{…}]}"}
```

- 原始长度 **3971** 字符，以合法的 `{"answer": "` 开头；
- 在**第 2921 字符**处出现 `\", \"groundedInText\":` —— `\"` 是转义引号，说明模型把**协议剩下的部分当成转义文本写进了 answer 字符串**；
- 全文没有出现未转义的 `"groundedInText"`；
- 正文里合法的转义引号数量为 **0**，所以「把结构性的 `\"` 去掉」对这段回答是**无损**的；
- 去掉之后恰好得到一个合法 JSON 对象：`answer` 长 **2829** 字符、`groundedInText: true`、`citations` **7** 条，全部是原文里真实存在的引文（其中第 5 条正是我们选中的 `where β ≥ 0 controls guidance strength and Zβ is the normalizing constant`）；
- 还原后的正文里没有任何 `"citations"`、`groundedInText`、`passageId`、`\"` 残留；`\log`、`\frac` 这些 LaTeX 反斜杠完好。

**判定：这是确定性恢复，不是猜测。** 规则只有两条守卫：

1. 正文 = 第一个 `\"` 之前的全部内容——由构造保证反斜杠处理不会碰到正文里本来就有的引号；
2. 还原后的文本必须能解析成对象，且 `answer` 是非空字符串、`citations` 是数组，否则放弃。

如果正文里本来就有合法的 `\"`，第 2 条会失败，于是放弃——只会「恢复不了」，不会「恢复出错误的东西」。这条规则有 6 个用例（含原始字节回放、无误导性断言、引用仍逐字校验）。

### 3.2 协议简化：为什么不继续加固修复器

失败的根本原因是结构性的：**一段 2800 字、满是 LaTeX 的中文回答被要求放进 JSON 字符串里**，任何一处转义错误都会毁掉整个回答。继续写更强的字符串修复器，是在给一个本不该存在的约束打补丁。

新协议（`server/prompt.mjs`）：

```text
（正文：纯文本，可以有换行；引用编号写 [1]；公式写在 $...$ 或 $$...$$ 里，反斜杠照原样写）

<<<CITATIONS>>>
{"groundedInText": true, "citations": [{"n": 1, "passageId": "selection", "quote": "…"}]}
```

正文不再经过 JSON 转义，所以**这类失败在结构上不可能再发生**。代价是失去 JSON 模式对输出的强制约束——这个代价见第九节限制 1。

`response_format: {"type":"json_object"}` 已从 DeepSeek 适配器移除（`server/providers/deepseek.mjs`），并有测试断言它不再被发送。

### 3.3 状态机

`parseModelOutput` 按固定顺序尝试，每一步都写明它对应什么状态：

| 顺序 | 输入形态                         | 状态         | `diagnostics.recovery`  |
| ---- | -------------------------------- | ------------ | ----------------------- |
| 1    | 正文 + 分隔符 + 合法引用块       | `valid`      | `sentinel`              |
| 1    | 正文 + 分隔符 + 只能逐字段读的块 | `recovered`  | `sentinel`              |
| 1    | 正文 + 分隔符 + 读不出来的块     | `recovered`  | `sentinel-broken-block` |
| 1    | 正文 + 分隔符，后面什么都没有    | `recovered`  | `sentinel-no-block`     |
| 2    | 旧协议的完整 JSON                | `valid`      | `legacy-json`           |
| 3    | 旧协议的破损 JSON，字段完好      | `recovered`  | `field-salvage`         |
| 4    | 转义进 answer 的协议（真实失败） | `recovered`  | `escaped-envelope`      |
| 5    | 纯散文，没有引用块               | `recovered`  | `prose`                 |
| 6    | 只有协议、没有可用正文           | `malformed`  | `protocol-text` 等      |
| —    | 提供方报告生成提前结束           | `incomplete` | 覆盖以上状态            |

`incomplete` 优先于解析结果：如果是截断导致解析失败，说「被截断」比说「无法解析」更接近事实。

**每一条恢复路径都仍然逐字校验引用。** 恢复的是形状，不是证据。

### 3.4 绝不显示协议

`looksLikeProtocol()` 是整个模块的兜底规则：**任何以 `{` 开头且能解析成对象的文本都不当作散文**（不只是认识字段名的那几种）。所以 `{"answer": 42}`、`{"other":1}`、`{"citations":[],"note":"oops"}` 一律 `malformed`，正文为空。

界面对 `malformed` 的做法是：一句说明 + 一个「重试」按钮，**不显示原始输出**。

### 3.5 诊断信息安全传出

服务端响应新增 `diagnostics`，只有数字与枚举：

```json
{
  "rawChars": 3971,
  "recovery": "escaped-envelope",
  "citationEntries": 7,
  "citationsAccepted": 0,
  "citationsRejected": 7,
  "finishReason": "stop",
  "truncated": false
}
```

没有提示词、没有论文文本、没有密钥。有测试断言 `verifyAnswer` 的返回值里没有 `isProvider` 之外的任何东西，且访问日志新增的 `outputStatus`/`finishReason` 都是枚举。

`finish_reason` 现在真的进了响应（Phase 4.1 第九节限制 3 提到的缺口），所以下一次联调能区分「模型自己收尾」与「上游截断」。

### 3.6 失败不干扰读者

新增用例：一次 `malformed` 回答之后，笔记数量不变（`malformed: an unreadable reply does not touch the reader's own work`）。原有的提供方错误用例继续断言高亮与笔记不受影响。

## 四、任务 B：无法解析时读者看到什么

| 情形                    | 界面                                                                    |
| ----------------------- | ----------------------------------------------------------------------- |
| `valid`                 | 正文 + 可点的引用；无额外提示                                           |
| `recovered`（结构问题） | 正文 + 一条说明「这次回答是按这条结构还原出来的，每条引用仍逐字校验过」 |
| `recovered`（无引用块） | 正文 + 「这次模型没有给出引用块，所以没有可校验的引用」                 |
| `incomplete`            | 正文 + 「模型没有写完就停了，下面是已经生成的部分」                     |
| `malformed`             | 「模型这次返回的内容没法还原成回答」+「重试」；**不显示任何原始输出**   |

- **不自动重试付费调用**：重试只能由读者点。
- **诊断信息默认折叠**：`<details>` 里的「技术细节」，展开才显示解析状态、结束原因、长度与引用条数。浏览器验收断言它默认是关闭的（`open` 属性不存在）。
- **不静默删改数学符号**：没有任何一处对反斜杠或符号做清洗；`\log`、`\frac` 在正文与 LaTeX 里都原样保留，并有测试断言。

## 五、任务 C：KaTeX 数学渲染

### 5.1 兼容性评估（先做，再实现）

| 项                 | 结论                                                                                       |
| ------------------ | ------------------------------------------------------------------------------------------ |
| 版本与许可         | KaTeX **0.19.0**，MIT；纯 JS，无原生依赖                                                   |
| 运行环境           | Node 22 下 `renderToString` 可直接用（构建与单测都跑得通）；浏览器侧无额外要求             |
| 与 React 19 的关系 | 无冲突：它只产出字符串，由我们把结果放进一个元素                                           |
| 离线可用性         | 样式与字体随包发布（Vite 把 `KaTeX_*` 字体打进 `dist/assets`），**不发出任何网络请求**     |
| 体积代价           | 主 JS 到 597 kB（gzip 185 kB）、CSS 到 60 kB（gzip 15 kB）；字体按需加载                   |
| 安全               | `trust: false` 关闭 `\href`、`\includegraphics`、`\htmlClass` 等能触及外部的命令           |
| 退化行为           | 解析失败时 `throwOnError: true` 抛错，由我们捕获后显示 LaTeX 原文，**不出现 KaTeX 错误框** |

### 5.2 实现

- 新组件 `src/features/reader/AiMath.tsx`；分段逻辑在 `src/services/ai/render.ts` 里扩展出 `math` 片段类型，引用编号仍在同一层处理，所以**公式旁边的引用照样可点**。
- 支持的定界符：`$…$`、`$$…$$`、`\(…\)`、`\[…\]`。落单的 `$`（价格、没写完的公式）保持为文字；`\$` 不当作定界符。
- `$$…$$` 可以跨行：分段只按空行切块，所以多行公式仍是一个公式。
- 超宽公式在 `.ai-math-block` 内横向滚动（`overflow-x: auto`），**面板溢出 0px**（实测）。
- 公式的 LaTeX 源码始终可得：元素上有 `data-latex` 与 `title`，展示型公式还有一个复制按钮（常显、半透明，悬停变实）。
- 深色/浅色主题都用现有设计令牌，`KaTeX` 继承 `currentColor`。
- **「回答里的公式是模型自己排版的 LaTeX，不是从 PDF 里提取出来的原文」** 这句说明在回答含公式时自动出现。

### 5.3 已验证

浏览器里对真实论文选中一段后要求「解释数学公式」：行内 `$R(u) := \log \frac{P_1(u)}{P_0(u)}$` 与展示型 `$$Z_\beta = \sum_u P_1(u) e^{\beta R(u)}$$` 都被排版；`data-latex` 保留原始源码（含 `\frac`）；一个比面板宽的公式在自身框内滚动而不是撑破面板；`\href{javascript:…}` 不产生 `<a>` 元素（单测）。

## 六、任务 D：PDF 数学输入的信任边界

### 6.1 选段 == 发送（不变量）

Phase 4.1 加的那条不变量保留并通过：每次提问都抓取实际发出的请求体，断言「发送的段落 == 选中的段落」。本轮 `verify:ai` 里它仍然是第一项检查之一。

### 6.2 碎片化检测与警告

新函数 `measureFragmentation`（`src/features/reader/layout.ts`）：统计选中的叶 span 中有多少**只有一个字符**。

- 判据：有效 span ≥ 6 且单字 span 占比 ≥ 50%；
- **空 span 不计入**——文字层里满是它们，算进去会把比值稀释成假阴性（这正是第一次跑验收时没触发的原因，见第八节缺陷 3）；
- 结果在**发送之前**显示在面板上，不在折叠区里：

  > 选中的这段原文在 PDF 文字层里是碎的：10 个片段里有 8 个只有一个字符，公式或符号很可能被拆成了单字。模型拿到的就是这些碎片，不是排版好的公式。

端到端验证：新造了一个**每个字形单独定位**的 PDF（`buildFragmentedPdf`），浏览器里选中那段并提问，警告如期出现（截图 `11-fragmented.png`）。

### 6.3 发送范围预览

原有的「查看会发送的范围」保留，折叠区里列出选中的原文、同页上文、同页下文与各自字数；碎片化警告与版面顺序警告放在折叠区**外**，因为它们是「要不要发」的判断依据，不该被藏起来。

### 6.4 不把模型推断的 LaTeX 冒充原文

- 引用列表里的 `quote` 是**逐字校验过的纯文本**，从不经过公式渲染——它是原文，不是排版；
- 回答正文里的公式则明确标注为模型自己的排版（见 5.2）。

### 6.5 可选：读者自己输入公式文本（仅评估，未实现）

评估结论：可行，但这一轮不做。

- **形态**：在浮动工具条里增加「这段公式其实是……」的输入框，读者手打 LaTeX，随请求一起发；服务端把它作为**单独段落**（`id: "user-formula"`）送出，并在提示词里标明「由读者提供，不是从 PDF 提取的」。
- **必须的安全边界**：它绝不能进入引用校验的候选池——否则「读者输入 + 模型引用 + 逐字校验通过」会伪造出一种「原文里有这个公式」的假象。引用只能来自 PDF 提取的段落。
- **不做多模态**：让模型直接看公式图片属于另一类能力（图像输入），本轮的证据不足以评价，且会引入新的图像传输与费用边界。
- **代价**：多一个输入控件、一条新的服务端字段、以及上面那条必须写进测试的边界。放到 Phase 5 与「公式区域框选」一起做更合适。

## 七、任务 E：Mock / 真实隔离与证据安全

### 7.1 分开的入口

```bash
npm run ai:serve:offline   # 强制 mock
npm run ai:serve           # 由 AI_PROVIDER 决定，默认 mock
npm run ai:serve:online    # 缺少 AI_PROVIDER=deepseek 或密钥就拒绝启动
```

`--online` 缺条件时输出两条原因并以 `exit=3` 退出，**不启动服务、不发出调用**（实测）。

### 7.2 端口：中止，不连接

`server/start.mjs` 监听 `error` 事件：`EADDRINUSE` 时打印原因并 `exit=3`，明确写出「不会改用别的端口，也不会去连接那个已经存在的服务」。

**实测（本轮最有说服力的一条）**：验收开始时，这台机器的 **8787 端口上还跑着 Phase 4.1 留下的付费 DeepSeek 服务**（`health` 显示 `provider: deepseek, online: true`）。在这个真实条件下：

| 动作                                    | 结果                                                           |
| --------------------------------------- | -------------------------------------------------------------- |
| 把离线套件指向 8787（`AI_VERIFY_PORT`） | `exit=4`，「端口上已有服务，本次验收不会使用它」——**没有连接** |
| 在 8787 上再启动一个服务                | `exit=3`，「端口已被占用，这次启动中止」                       |
| 在带密钥的环境里启动 `--offline`        | 正常起来，日志写明「环境里的 AI_PROVIDER 与密钥都被忽略」      |

Phase 4.1 那次误发的真实调用，正是「桩件没拿到端口，请求打到了已有服务」。这两条现在都不可能再静默发生。

### 7.3 身份校验，而不是可用性校验

验收套件启动服务后，必须读到 `provider === "mock"` 且 `online === false` 才继续；否则杀掉自己的子进程并报错。区分「有东西应答」与「是对的那个东西」，是 Phase 4.1 的教训。

### 7.4 调用次数断言

新增：`calls: exactly one request left the page for each question asked, with no retries` —— 页面发出的请求数必须等于脚本发起的提问数（本轮 13 = 13）。服务端侧的「一次提问恰好调用一次 provider」仍由既有单测保证。

### 7.5 证据安全

- 截图与报告写到 `docs/screenshots-phase4.2/<运行时间戳>/`，**每次运行一个新目录，永不覆盖同名文件**；
- 脚本里没有任何删除操作；
- 本轮我自己清理时，先列出全部 7 个运行目录、确认前 6 个是中途失败的重复产物，才逐个删除（保留了最终 54/54 的那一次）。这是删除**本轮自己刚生成的重复产物**，不是别人的证据。
- **但**：重跑 `verify:annotations` / `verify:reader` / `verify:real` 会覆盖它们各自固定路径下的历史截图与报告——本轮就发生了。我已经用 `git checkout` 把它们还原，并把「这三个套件仍写固定路径」列为限制 6。

## 八、本轮自己发现并修复的三个缺陷

这三个都不是设计时想到的，是跑出来的。

### 缺陷 1：恢复出来的长回答会让下一次提问变成 400

`verify:ai` 跑到「截断」那一步时停住：追问的响应是 **400**。原因是会话历史把上一条 **2829 字**的回答原样带了回去，而服务端对单条 history 的上限是 **2000 字**，于是整个请求被判为不合法。

修复：`buildHistory`（`src/services/ai/context.ts`）——没有回答的轮次不进入历史、空回答不进入历史、单条超过 2000 字截断并加省略号。6 个单测。这条只有在「真的问三个问题」时才会暴露。

### 缺陷 2：深色主题下「技术细节」的标签对比度 4.23:1

验收的对比度审计报 `[4.23 < 4.5 dt "引用"]`。`.ai-diagnostics dt` 用了 `--text-3`，在深色面板上不够。改为 `--text-2`，值改用 `--text`。重跑后两种主题 71 个文本片段全部达标。

### 缺陷 3：碎片化检测被空 span 稀释

第一次跑碎片化验收时警告没出现。原因是：文字层里在可见 span 之间夹着大量**空 span**，它们被算进了分母，把「8/10」稀释成「8/20」。修复：分母只数有文字的 span，并补了一个「每个字形后面跟一个空 span」的单测把行为锁住。

## 九、未解决的限制

1. **新协议还没有被真实模型验证过。** 这是本轮最重要的限制：`<<<CITATIONS>>>` 分隔符协议只在 mock 与历史响应回放上验证过。真实模型会不会遵守、遵守率多少、`recovered/prose` 会不会变成常态，**需要一次真实联调才能回答**，而本轮明令禁止。下一次联调必须在报告里记录 `status` 分布。
2. **取消 JSON 模式是一个权衡。** 换来了「正文不可能被转义毁掉」，代价是模型不再被强制输出结构化内容；没有引用块时界面只能显示「无可校验引用」。
3. **真实失败样本只有一条。** `escaped-envelope` 规则的形状来自这一次实测；其他模型的同类失效形态没有证据。
4. **碎片化判据是启发式的。** 「单字 span 占比 ≥ 50%」在混合内容（公式 + 短词）上可能偏保守或偏激进；本轮没有真实论文的公式区域样本量来调参。
5. **读者自输公式文本未实现**（见 6.5），多模态评估未做。
6. **三个旧验收套件仍写固定路径**（`verify:annotations`、`verify:reader`、`verify:real`），重跑会覆盖它们各自的历史证据。本轮已还原，但修它们属于 Phase 2–4 的脚本，不在本轮范围。
7. 未做流式输出；对话仍不持久化；未接任何其他模型。
8. 费用与用量本轮为 **0**，没有任何 `usage` 数据。
