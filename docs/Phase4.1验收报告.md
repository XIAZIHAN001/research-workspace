## 三、关卡 A：离线修复

### 缺陷 1（真实兼容性缺陷）：思考模式默认开启，且推理与正文共用 `max_tokens`

官方默认 `thinking: enabled` + `reasoning_effort: high`，而旧代码既没有显式发送这两项（等于接受上游默认），又只申请 `max_tokens: 2048`。真实论文段落上，一次长思考会把预算耗尽，`content` 变成空串——而旧代码会把它当成正常回答。

修复：显式发送 `thinking` 与 `reasoning_effort`（默认 `low`）；`DEEPSEEK_THINKING=disabled` 时强制档位为 `none`（避免发出自相矛盾的请求）；空内容按 `finish_reason` 分类报错；记录 `reasoning_tokens`。

### 缺陷 2：402（余额不足）被归为「限流，请稍后重试」

等待不会让余额变多，这个提示会把用户引向错误的方向。改为独立的 `insufficient-balance`，并明确「重试不会有用」。

### 缺陷 3：400 / 422（参数不合法）被归为「模型服务返回了错误」

这其实是**我们构造的请求**被拒绝，报成上游故障会误导排查方向。改为独立的 `invalid-request`，文案说明这是应用的配置问题。

### 缺陷 4：`finish_reason` 只识别 `length`

补齐 `insufficient_system_resource`（服务中途资源不足）与 `aborted`：两者都意味着回答不完整，却不会表现为截断。

### 缺陷 5（脚本）：测试辅助函数把部分配置传给服务

`startTestService` 里 `{ config, ...deps }` 的顺序让 `deps.config` 覆盖了合并后的配置，于是 `allowedOrigins` 丢失，跨源请求从「403 拒绝」变成「崩溃」。

### 缺陷 6（产品，联调时暴露）：AI 菜单可以渲染到窗口下方，点不到

选段靠近页面底部时，浮动工具条按 `top = spot.y - 12` 定位，只夹住了上边界。点开 AI 菜单后菜单向下展开，最后几项落到窗口之外——Playwright 报 `element is outside of the viewport`，真实用户则根本点不到「翻译为中文」。

修复：纵向也做夹取（按状态估算高度，`window.innerHeight - 估算高度 - EDGE`），并在样式表加 `max-height: calc(100vh - 120px); overflow-y: auto` 作为兜底——估算偏小时菜单内部滚动，而不是消失。

这条是**联调直接阻塞**才发现的：mock 验收里选段都在页面中部，从来没触发过。

### 新增的边界测试（A2）

全部**统计 provider 的调用次数**，因为「拒绝了」只有发生在计费调用**之前**才成立：

| 断言                       | 结果                                                                                                                                                                                    |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 跨源 POST                  | 403，且 provider **未被调用**                                                                                                                                                           |
| DNS rebinding（伪造 Host） | 403，且 provider **未被调用**                                                                                                                                                           |
| 超大请求体                 | 拒绝，且 provider **未被调用**                                                                                                                                                          |
| 一次提问                   | provider 恰好被调用 **1 次**（不重试）                                                                                                                                                  |
| health 载荷                | 不含凭据；且报告在线提供方将花什么（`reasoning`）                                                                                                                                       |
| 访问日志                   | 不含凭据、不含论文正文                                                                                                                                                                  |
| `readConfig`               | 除 `DEEPSEEK_API_KEY` 外**不读任何凭据**（断言 `ANTHROPIC_API_KEY` / `CLAUDE_CODE_OAUTH_TOKEN` / `OPENAI_API_KEY` / `AWS_SECRET_ACCESS_KEY` / `GITHUB_TOKEN` 的值没有出现在配置对象里） |
| 凭据只出现一次             | 用带特征值的密钥断言它在序列化配置里只出现 **1 次**                                                                                                                                     |

### A3：引用合法 / 有依据 / 正确 —— 三者分开

| 问题                               | 谁来判                 | 本服务的态度                                                         |
| ---------------------------------- | ---------------------- | -------------------------------------------------------------------- |
| 引用文字是否真的来自本次提供的原文 | **服务端**（逐字比对） | 保证。不合格的引用被丢弃并计数，绝不显示成可点链接                   |
| 原文是否支持这句话的结论           | 读者                   | **不检查**（用第二个模型给第一个模型打分，只是把不可验证换了个位置） |
| 结论本身是否正确                   | 读者                   | **不检查**，也检查不了                                               |

写成测试而不是散文：两个用例——**引文真实但结论是原文没说的**、**引文真实但推导凭空捏造**——都会「完全通过校验」，这正是这一层敢承诺的全部。`verifyAnswer` 是纯函数，因此「没有第二次模型调用」是结构性质而非承诺。

界面已改写两处文案：

- 每条引用下方：「以上引用已核对：引文确实逐字来自本次发送给模型的原文。引文是否支持这里的结论、以及结论本身是否正确，不在这道校验的范围内。」
- `groundedInText`：「模型自己认为提供的原文不足以完整回答这个问题。这是它的自述，不是被核对过的事实。」

### A4：`browser disconnected`

Phase 4 报告中那条记录是**测试收尾时 `browser.close()` 触发的**——它在全部 28 项检查**之后**才被写入，所以那次是全绿通过。处理器分不清「收工」与「崩溃」。已加 `closing` 标志，重跑后 `consoleIssues` 为 `[]`。

### 4.5 公式解释（返回成功，但 JSON 不完整）

**选段**（实测确认发送内容 == 选中内容）：`where β ≥ 0 controls guidance strength and Zβ is the normalizing constant`

- HTTP 200，21,299 ms，输入 888 / 输出 4231 token（推理 2261）。
- **回答内容本身质量很高**：逐项说明了 $E \subseteq [N]\setminus T$、$z\setminus E$、$P_1$、$P_0$、$R$、$\beta$、$Z_\beta$、$Q_\beta$；给出了四步推导；把「原文明确给出的前提」与「数学上需要但原文未给的前提」分开列；明确指出提取缺陷（分式横线丢失、公式 (4) 被分段、脚注上标丢失）；对每个补充都标了「补充」。
- **但整段是按纯文本降级显示的**：模型返回的 JSON 没有闭合，`JSON.parse` 失败，于是走了既定的降级路径——正文照录 + 警告「模型没有按约定返回 JSON，因此没有可校验的引用；下面的内容是原文照录」。**因此这一次的 0 条引用不是引用错误，而是根本没有机会校验。**
- 为什么不是预算问题：`completionTokens` 4231 < 8192，且 `finish_reason` 不是 `length`。是这个回答的 JSON 结构本身坏了（见 4.7）。

### 4.6 联调后据实修改的两个参数

| 参数                                           | 原值 | 新值      | 依据                                                               |
| ---------------------------------------------- | ---- | --------- | ------------------------------------------------------------------ |
| `LIMITS.answerTokens` / `AI_MAX_OUTPUT_TOKENS` | 4096 | **8192**  | 案例 1 用了 3802/4096（推理 2689，仅余 294）；案例 2 直接耗尽      |
| `DEFAULT_TIMEOUT_MS`                           | 60 s | **120 s** | 实测 21 s / 25 s，8192 下可能接近一分钟，60 s 会把慢答案变成慢失败 |

另：health 载荷新增 `answerTokens`，让联调记录**自己说明是哪个上限产出的结果**，也避免「变更前启动的进程冒充变更后的进程」——本次正是靠这个字段发现服务是旧进程。

### 4.7 实测发现：模型会在 JSON 字符串里写 LaTeX

案例 6 的输出以一个合法的 `{"answer": "` 开头，然后整段正文，末尾是 `…demonstrations.\"}]}`——**答案字符串从未闭合**，评分器扫描到文件结尾仍处于字符串内部。也就是说模型把后续的 `"groundedInText": true, "citations": […]` 当成**转义过的文本**写进了 `answer` 里。

这是 JSON 输出模式下一个真实的失效形态，且官方文档保证的「valid JSON」在这一次没有成立。本次的处理与结论：

1. **降级路径按设计工作**：正文照录 + 明确警告，读者不会看到一段被当成答案的 JSON、也不会看到 0 条引用却不明白为什么。
2. **新增保守的字段级恢复**（`server/citations.mjs` 的 `salvage`）：JSON 整体解析失败时，逐个读取 `answer` 字段与每个 `citations` 对象；每个引用对象**单独**过 `JSON.parse`，坏掉的丢弃；恢复出来的引用**仍然逐字校验**，并加一条警告说明「没有经过一次完整的 JSON 解析」。带 4 条单测。
   - 对案例 6 这一次它救不回来（答案字符串本身没闭合），因此这次仍然按纯文本显示——这是正确的：不猜。
3. 没能确认的：`finish_reason` 没有随响应进入记录。已建议（但本轮未实现）把它加进服务端响应，下一次就能判断是模型自己收尾还是上游截断。

### 5.2 删掉了两张真实截图

清理干跑残留时使用通配符 `rm docs/screenshots-phase4.1/3*-live-*.png`，**把上一次真实调用的 `31-live-explain.png` 与 `33-live-translate.png` 一并删除**。二者未被提交过，无法恢复。同一批清理也删除了记录那次意外调用细节的 JSON。

### 5.3 选段索引错位——所有检查都在验证我自己的意图

`spanInfo`（我的脚本）在枚举文字层时过滤掉了空 span，而 `selectSpans` 按**全部**叶 span 编号。两个索引基准不一致，于是「我选中的段落」和「应用实际选中的段落」不是同一段。

后果：第一次 8192 的公式调用里，脚本记录的是 `(4)whereβ≥0…`（71 字符，3 个符号），**模型实际收到的是 `P0(u) := P`**（11 字符）。而「选段确实含符号」这条检查**照常通过**——它在检查我自己的字符串，不是发出去的东西。这是本轮最危险的一个错误：它能让一整套检查全绿而结论错误。

暴露方式：模型的回答里写着「你选中的行只有「P0(u) := P」」，与记录对不上。

修复两件：

1. `spanInfo` 保留全部叶 span（含空），索引与 `selectSpans` 对齐；
2. **新增一条不变量检查**：每次提问都抓取实际发出的请求体，断言「发送的段落 == 选中的段落」。这条检查如果在最初就有，会在第一次就抓住这个 bug。

## 八、未解决的限制

1. **公式案例的回答没有通过 JSON 校验**（见 4.7）。正文质量高，但它是以纯文本降级显示的，0 条引用因此没有被检验——不是引用错误，是没机会校验。根本原因是模型把后续 JSON 转义进了 `answer` 字符串。保守的字段级恢复已实现，但救不回这一种形态。
2. **解释与翻译没有浏览器截图**（见 5.2）。
3. **`finish_reason` 没有进入服务响应**，所以无法判断案例 6 是模型自己收尾还是上游截断。建议下一轮加进响应体。
4. **原文解释耗时 21 秒**。思考模式下的延迟对阅读体验是真实成本；面板已显示推理 token 数，但没有流式输出，等待期间只能看到「正在请求模型…」。
5. **`groundedInText` 仍是模型自述**，本轮未做任何独立验证——这是刻意的（见第三节 A3）。
6. **引用合法性 ≠ 结论正确性**：本轮只有人工评价，没有可重复的机器判据。
7. **公式/符号的提取仍是碎的**：这篇论文的排版公式在文字层里被切成单字符（`≥`、`∈`、`) :=`、`∏`），所以"解释公式"这个用例只能退而选一段**用符号下定义的散文**。真正的排版公式解释能力，本轮的证据不足以评价。
8. 真实样本仍只有两篇英文双栏 CC BY 4.0 论文；中文论文、扫描版、表格密集论文未验证。
9. 未做流式输出、未接 KaTeX、对话不持久化（沿用 Phase 4 的限制）。
10. 成本与用量只来自 API 返回的 `usage`；**没有对账**（未查 DeepSeek 控制台的账单），因此报告中的费用是估算而非凭证。

## 九、恢复现场

三个案例都已取得真实结果，正常情况下不需要再跑。要复现或重跑其中某一个：

第一步，在**你自己的终端**启动服务。Windows 默认终端是 PowerShell，`VAR=value command` 是 bash 写法，PowerShell 会把它当成命令名去找并报 `The term 'AI_PROVIDER=deepseek' is not recognized`：

```powershell
$env:AI_PROVIDER='deepseek'; $env:DEEPSEEK_API_KEY='…'; npm run ai:serve
```

（bash / Git Bash / macOS / Linux 才是 `AI_PROVIDER=deepseek DEEPSEEK_API_KEY=… npm run ai:serve`。）

第二步，只跑你需要的那一个案例，不会重复消耗已经取得答案的另外两个：

```bash
npm run verify:live -- --only=formula
```

`--only=formula` 只跑公式一个案例，不会重复消耗已经取得答案的解释与翻译。
